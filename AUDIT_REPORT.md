# IntelliReq — Full Repository Audit Report

## 1. Current Architecture
The current architecture follows a hybrid machine learning approach:
*   **Preprocessing & Feature Extraction**: A `FeatureExtractor` module identifies explicit linguistic ambiguity indicators (e.g., vague adjectives, subjective terms) and specificity markers (e.g., measurable numbers, thresholds, units).
*   **Semantic Extraction**: An `SBERTExtractor` produces 384-dimensional dense semantic embeddings using `sentence-transformers` (`all-MiniLM-L6-v2`).
*   **Model Fusion**: The linguistic, specificity, and semantic features are concatenated.
*   **Classification**: A Calibrated Logistic Regression model (with L1 penalty) predicts the probability of ambiguity.
*   **Inference & Explanation**: A `ModelPredictor` handles borderline cases and specificity overrides, while an `ExplanationEngine` uses the linguistic features to construct a human-readable justification for the prediction.

## 2. Current Dataset Sources
*   `dataset/software_requirements.csv` (Base source)
*   `data/ambiguity_dataset_v2.csv` (Currently generated dataset of ~634 rows)
*   `data/challenge_test_set.csv` (100-row held-out challenge set)
*   Various exploratory datasets (`software_requirements_extended.csv`, Excel files) accessible via `dataset_inspector.py`.

## 3. Label-Generation Methodology
The current dataset (`ambiguity_dataset_v2.csv`) relies heavily on **strict pseudo-labeling heuristics** implemented in `generate_dataset.py`.
*   Requirements containing vague words (e.g., "quickly", "easy") but no specific numbers are automatically labeled "Ambiguous".
*   Requirements containing specific metrics but no vague words are automatically labeled "Not Ambiguous".
*   A small set of 12 "controlled pairs" (24 sentences) is injected to provide adversarial examples.

## 4. Current Class Distribution
The dataset generation script attempts to balance the pseudo-labels (target: 700 each), but the actual current `ambiguity_dataset_v2.csv` contains roughly 634 rows, split evenly between Ambiguous and Not Ambiguous, plus the controlled pairs.

## 5. Current Feature Pipeline
*   **Semantic**: 384 SBERT dimensions.
*   **Linguistic**: Vague Term Count, Subjective Term Count, Approximate Quantity Count, Undefined Reference Count, Modal Verb Count.
*   **Specificity**: Has Numeric Value, Percentage, Time Unit, Size Unit, Capacity Value, Threshold, Range, Format, Explicit Condition, Testable Constraint.

## 6. Current Model
The final selected model is a **Logistic Regression** (L1 penalty, `liblinear` solver, balanced class weights) wrapped in a `CalibratedClassifierCV` (sigmoid, cv=5) after standard scaling.

## 7. Current Evaluation Methodology
*   The training pipeline splits data 70/15/15 (Train/Val/Test).
*   Stratification is based on `Source` + `Ambiguity_Label`.
*   Metrics: Accuracy, Precision, Recall, F1.
*   Independent evaluation is conducted on `data/challenge_test_set.csv` via `evaluate_challenge.py`.

## 8. Potential Leakage
*   **Tautological Label Leakage**: Because the labels in the training set are largely generated by the exact same regex rules used in the linguistic feature extractor, the model is simply learning the heuristic rules rather than genuine semantic ambiguity.
*   **Split Leakage**: Stratified splitting by `Source` does not inherently prevent duplicate requirements, near-duplicates, or identical templates from appearing in both the training and test sets.

## 9. Potential Overfitting
Due to the tautological labels, the model can easily achieve near 100% internal test accuracy by placing high weight on the linguistic features (which perfectly correlate with the pseudo-labels). This is overfitting to the rule-based label generation.

## 10. Potential Underfitting
The model performs poorly (e.g., 64% accuracy) on the challenge test set. This indicates underfitting to true linguistic complexity, as SBERT struggles to discern nuance (like the presence of a number alongside a subtle vague term) when it has only been trained on simplistic, rule-generated extremes.

## 11. Current False-Positive Patterns
Requirements that are fundamentally clear but contain a word technically matched by the subjective regex (e.g., "modern web framework") might be flagged as ambiguous because the model places excessive weight on those keywords due to the training data bias.

## 12. Current False-Negative Patterns
Requirements that contain a numeric value but still include an undefined qualitative term (e.g., "process 500 requests efficiently") risk being overridden. While a recent precision guard (`ling_score == 0`) attempts to fix this, the model's underlying probabilities are still skewed by the training data.

## 13. Current Batch Processing Limitations
`main.py` currently only supports `.csv` inputs via `pd.read_csv()`. It hardcodes a check for specific column names (`Requirement`, `Requirement_Text`, `text`, `requirement`) and fails if none are found. It does not support `.xlsx`/`.xls`, does not allow interactive column selection, lacks row-level error handling (one bad row could crash processing), and does not export formatted Excel reports.

## 14. Recommended Changes
1.  **Dataset Overhaul**: Archive `ambiguity_dataset_v2.csv`. Generate `intellireq_clean_dataset.csv` manually or using strict quality guidelines with a large volume of diverse controlled pairs.
2.  **Dataset Quality Enforcement**: Implement `dataset_quality.py` to proactively block exact/near duplicates and ensure group-aware splitting (so controlled pairs don't cross train/test boundaries).
3.  **Pipeline Restructuring**: Update `train_pipeline.py` to use group-aware splits and report true unbiased test metrics without chasing 100%.
4.  **Batch Processing Upgrade**: Refactor `analyze_batch()` in `main.py` to support pandas Excel parsing, interactive column selection, row-level `try/except` blocks, and multi-sheet Excel exporting (`openpyxl`).
5.  **Documentation & Guidelines**: Write `docs/annotation_guidelines.md` and rewrite `README.md` to reflect a scientifically defensible approach.
